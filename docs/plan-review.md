# 구현 계획 검토 — Hyochang Eats

- 검토 대상: `docs/implementation-plan.md` (2026-11-14 초안)
- 검토 기준: PRD 요약(세션 배경), 실제 코드(`app/[lang]/`, `components/`, `data/`, `lib/`, 설정 파일), `node_modules/vinext/README.md`(vinext 1.4.5)
- 검토자: 독립 리뷰어 (코드·계획은 수정하지 않음)
- 확인한 것: `npx tsc --noEmit --incremental false` 통과(오류 0). 샘플 6곳 모두 역에서 192~482m(500m 안). 빌드 산출물 `.cloudflare/output` 번들(소스맵 제외) gzip 약 356KB.
- 확인하지 못한 것: 실제 배포, 실기기 동작, Cloudflare·OSM·Umami의 현재 약관과 한도(아래에서 "기억 기준"이라고 표시한 부분은 공식 문서로 다시 확인해야 함).

## 1. 판정 (3문장)

계획의 기술 방향(정적 데이터, 서버·DB 없음, `[lang]` 세그먼트 i18n, Leaflet을 클라이언트에서만 불러오기)은 맞고, 코드도 그 방향대로 깔끔하게 짜여 있다.
하지만 일정이 "개발 작업" 중심으로 짜여 있어서, 정작 출시 기준인 **실제 맛집 30곳 직접 검증·촬영·이중언어 작성**이 3·4주차에 목표가 없고 5주차에 몰려 있으며, 도메인·개인정보처리방침·테스터 모집·홍보 같은 출시 준비가 너무 늦거나 빠져 있다.
초보 1인 개발 기준으로 시트 가져오기·Playwright·GitHub Actions·두 가지 공유 링크 방식은 빼고, 그 시간을 데이터 수집과 1주차 배포 판단(명확한 기준 + Workers 무료 CPU 한도 확인)에 쓰면 5주 출시가 현실적이 된다.

## 2. 발견 사항 (심각도순)

심각도 기준 — **치명**: 고치지 않으면 5주차 출시 기준을 못 맞출 가능성이 큼 / **높음**: 출시 시점에 사용자·법·운영 문제로 이어짐 / **중간**: 품질·비용·시간 낭비 / **낮음**: 정리하면 좋은 것.

## 4. 그대로 두어도 되는 결정

- 서버·DB·로그인 없는 정적 데이터 구조, "데이터 변경 = 재배포" (§3).
- `[lang]` 세그먼트 + 코드 사전 i18n, next-intl 미사용 (D5).
- 사진은 직접 촬영만, 파일 크기 상한과 존재 여부를 검증 (D3-6, D10).
- 빌드 시 500m 반경·카테고리·태그·이중언어 누락 검사 (D3 1~4). 반경 규칙이 PRD 범위를 코드로 지켜 준다.
- 분석 호출을 `lib/track.ts` 한 곳에 모으기, 이벤트 3종으로 시작 (D7).
- 길찾기: 네이버 플레이스 고유 주소 우선, 구글은 좌표 대체, 국내 구글 길찾기 제한은 실기기로 확인 (D8).
- 목록만으로 모든 기능 사용 가능, 색+글자로 카테고리 구분 (D12). 현재 코드도 칩에 글자가 있음.
- `checkedAt` 표시와 제보 폼(구글 폼, 가게 id 미리 채움) (D11).
- 위치를 저장·전송하지 않고, 거부 시 역 기준 정렬로 되돌리기 (D9, `components/Explorer.tsx:48`).
- "이후" 기능(즐겨찾기, 리뷰, 로그인, 코스, 네이티브)을 출시 뒤로 고정 (§7).
